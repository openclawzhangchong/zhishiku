# 33 · Android音效撤回：引擎级差异、真机音质A/B、覆盖式回滚

> **摘要**：v2.0.0 把桌面端音效（8 款音效 + 均衡器）移植到 Android APK，代码实现零缺陷、功能链路真机全过——但用户**实测一天后判定：开启音效音质大幅下降，方案不可行**。根因是**引擎级平台差异**：桌面 Chromium 的 DynamicsCompressor 自带约 +9.5dB 自动 makeup，我们用 safetyGain=0.30 补偿后 limiter 透明；**Android WebView 没有这个 makeup 行为**，0.30 直接把声音衰减到 30%，limiter 压缩特性也不同——引擎级差异，不可调参修复。本篇沉淀：桌面验收通过 ≠ 移动端可用；真机验收必须含音质 A/B 对比；回滚版本的 versionCode 必须递增；Release 撤回用标注不用删除。

**关键词**：Android WebView、Web Audio 平台差异、DynamicsCompressor makeup、音质 A/B 对比、回滚 versionCode 递增、Release 撤回标注、双版本并存、默认关闭

## 事故 1：桌面验收全过 → 移动端音质大幅下降

| 项 | 内容 |
|---|---|
| **症状** | 用户真机实测一天后反馈：开启音效后**音质大幅下降**（压缩感、响度骤减） |
| **错误归因** | "实现有 bug" / "参数没调好" —— 代码层审查（双实现 agent + 双独立审查 agent）确实零缺陷 |
| **证据链** | ① 桌面端（Chromium Windows）8 款音效真机验收**满意**（v1.7.6）② 移动端功能链路真机全过：息屏 20s / 切后台 30s 播放不断、9 按钮渲染、切换持久化 ③ 用户实测结论：**音质下降太多，不可接受** ④ 技术归因：Android WebView 的 DynamicsCompressorNode **没有桌面 Chromium 的自动 makeup gain**（约 +9.5dB，Chromium 特有行为、spec 外），而桌面端已用 safetyGain=0.30 补偿该 makeup——同一参数在 Android 上直接把声音衰减到 30% |
| **根因** | **Web Audio 引擎级平台差异**。桌面验证通过掩盖了移动端音频质量未验证的事实。参数补偿只在"makeup 存在"的平台成立 |
| **为什么没早发现** | ① 真机验收清单只测了「功能链路」（有声/能切换/息屏不断），**没有音质 A/B 对比项** ② 桌面回归通过造成了"已经验证过"的错觉 ③ 无真机阶段无法做音质对比（这是当时已知的验证盲区，但没有为此设计最早的真机验证项） |
| **修复** | 按用户决策**全面回滚**：audioService 三处门控恢复 `!isElectron` 即禁用；自愈挂载点注释（方法体保留）；移动端 UI 入口/面板/开关注释保留；v2.0.1 发布（versionCode 2004 > 2003，从 2.0.0 直接覆盖）；v2.0.0 Release 标注撤回；ECS 撤下 2.0.0 保留 1.6.0 |
| **可复用教训** | **桌面验收通过 ≠ 移动端可用。** Web Audio 这类"平台引擎行为"功能，真机验收第一项必须是**与旧版的音质 A/B 对比**，功能链路测试只是及格线 |

> 平台差异的具体技术点：桌面 Chromium 对 DynamicsCompressorNode 施加 spec 外的自动 makeup（Chromium issue 372198644），Android WebView（同 Chromium 内核不同平台构建）该行为缺失/不同。**补偿参数不可跨平台复用。**

## 事故 2：回滚时的版本链陷阱

| 项 | 内容 |
|---|---|
| **症状** | 需要让已安装 2.0.0（versionCode 2003）的用户回到"无音效"状态 |
| **错误归因** | "直接重新分发 1.6.0.apk 就行" |
| **证据链** | Android 签名机制：**versionCode 必须递增才能覆盖安装**。1.6.0 的 versionCode（1603）< 2003，装了 2.0.0 的设备无法直接覆盖回 1.6.0，必须卸载（丢数据） |
| **根因** | 回滚包版本号跟着"功能回退"走，忽略了升级链的**单调性约束** |
| **修复** | 出 **2.0.1（versionCode 2004 > 2003）**：内容 = 移除移动端音效（行为回归 1.6.0），但版本号单调递增。装了 2.0.0 的用户**直接覆盖安装**，数据无损 |
| **可复用教训** | **任何回滚包的 versionCode 必须 > 被回滚版**。回滚的是"功能"，不是"版本号"。versionName 可以表达"回归"语义（如 2.0.1 = 回到 1.6.0 行为），versionCode 只能往前走 |

## 方法论 1：Release 撤回用标注，不用删除

```text
PATCH /repos/{owner}/{repo}/releases/{id}
{
  "name": "v2.0.0 ...（❌ 已撤回——原因）",
  "body": "⚠️ 此版本已撤回，请勿下载使用\n\n原因：...\n\n处理：覆盖安装 v2.0.1 即可...（引导替代版本）"
}
```

- 不删除 release/tag（历史可查、已装用户有据可依）
- 撤回原因写明**技术归因**（给未来维护者）+ **替代版本链接**（给已装用户）
- 同时从分发渠道撤文件：ECS 删除对应 .apk（下载列表页自动消失）
- 若该 release 是 latest（非 prerelease），需要一个新的非 prerelease release 顶替 latest 位置

本项目实际操作（2026-11-03）：v2.0.0 标题改「❌ 已撤回」，正文写原因 + 引导 v2.0.1；同日发布 v2.0.1 正式版顶替 latest。

## 方法论 2：功能回滚的代码处理（保留 vs 删除）

移动端音效回滚时选择**注释保留**而非删除，原则：

| 内容 | 处理 | 理由 |
|---|---|---|
| 平台差异原因说明 | **写进代码注释**（标注版本号 + 简述） | 防止将来有人再放开 |
| audioService 三处门控 | 恢复原判断，v2.0.0 的判断**注释保留** | 备将来恢复 |
| setupMobileResilience / fallbackToBypass 方法体 | **保留**，挂载点注释 | 实现有价值；用 `void this.xxx` 在 dispose 里引用，防 TS6133 |
| UI 入口/面板/开关（模板+script+import） | **注释保留**，import 同步注释 | 避免 TS6133/unused 报错 |
| localStorage key | 无需清理 | 默认 false 无副作用 |

**typecheck 陷阱**：注释掉引用后，原 import 和未挂载的私有方法会报 TS6133/TS6192（unused）。
处理：import 同步注释；私有方法用 `void this.method;`（在 dispose）保持引用。

## 方法论 3：双版本并存的下载页形态

音效版（2.0.0）撤回后，下载页最终形态：

| 文件 | 标签 |
|---|---|
| `ZCMusic-2.0.1.apk` | 当前推荐（回归版） |
| `ZCMusic-1.6.0.apk` | 经典稳定版（长期保留） |

下载页服务端按文件名映射标签字典（LABELS），新增/删除版本文件名**需同步更新字典**。
用户侧同签名互覆盖、数据互通，"选错版本"的成本为零。

## 一页速查

| 场景 | 做法 |
|---|---|
| 桌面功能移植到移动端（涉及平台引擎行为） | 真机验收第一项 = **与旧版音质/表现 A/B 对比**，功能链路只是及格线 |
| 回滚已发布的坏版本 | 新包 versionCode **递增**；内容=移除问题功能；Release 标注撤回+引导替代 |
| Release 撤回 | PATCH name/body，不删 tag；分发渠道（下载页）同步撤文件 |
| 回滚代码 | 平台差异原因写进注释；实现保留挂载注释；import 同步注释防 unused 报错 |
| 用户实测发现"功能能用但体验差" | 这是**产品级否决**，优先级高于代码级"没有 bug"——不要试图用调参说服用户 |
