## 怎么用

**开工前** — 扫一遍 `14_通用铁律速查.md`（100 条，A–I 九类），多数低级错误能提前拦掉。

**遇到故障** — 按上表定位主题篇，看「踩坑清单」的四列：【现象】【根因】【修复】【可复用规则】。

**做新东西** — 找对应篇的「成功配方 / 具体实现」章节，里面是可照抄的清单（配色表、字号表、架构分层、脚本模板、命令）。

**让 AI 用** — 把 `00_总索引.md` 或具体主题篇投喂给你的 AI 助手，它能在开工前就知道这个环境里哪些坑不能踩。

## 贯穿全库的 12 条顶层原则

1. **先方案、后动手** — 改动前出 PLAN md，批准后才改代码。
2. **证据优于猜测** — 任何诊断必须带文件:行号、日志时间线、对照实验数据。
3. **回滚锚点常在** — 动手前打锚点 tag，失败过的 tag 永不复用。
4. **单一真相** — 一仓一种推送通道，一份文档一个真相源，改了必回填。
5. **绝不说失败是成功** — CI 红灯如实标记，严禁长期挂"待验证"。
6. **改共用东西前先查谁在用** — 共用回调、公共变量是事故高发区。
7. **状态位必须 finally 复位** — 忙标志、开关、连接标记，异常路径也要复位。
8. **验证跑完整链路** — 只复制两个函数做验证 = 漏掉加载期崩溃。
9. **确定性验证优于随机冒烟** — 精确注入状态 + 真实 `update()` 才能命中窄分支。
10. **批量授权、一次问清** — 一次解决 5–7 个决策点，别中途反复打断。
11. **大改动分批** — 先做一份验收，通过后再推全量。
12. **经验立刻 Skill 化** — 踩过的坑当天写进技能文件，否则下次必重踩。

## 如何补充

新踩的坑，按主题补写进对应篇，并**同步补一条进 `14_通用铁律速查.md`** —— 这是本库保持有用的唯一机制。

条目格式建议：

```
| 现象 | 根因 | 修复 | 可复用规则 |
```

一句话说不清的，附最小复现或对照实验数据。
